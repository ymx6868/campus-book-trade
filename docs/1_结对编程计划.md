## 二、沟通机制

### 2.1 沟通方式
- **主要方式：** 面对面（同宿舍）
- **辅助方式：** 微信群、视频共享屏幕
- **每日同步：** 每天简短Standup（10-15分钟），讨论当天计划

### 2.2 工作时间
- **每日固定时间：** 14:00-18:00, 19:30-22:00
- **结对编程时段：** 至少保证每天3小时同步在线开发

### 2.3 决策机制
- **技术方案分歧：** 列出各方案利弊，对比选优；无法决定时请教老师
- **任务优先级：** 共同评估，标记 P0(必做)/P1(应做)/P2(可做)
- **代码风格：** 后端遵循PEP8（Python），前端遵循ESLint + Prettier

## 三、冲突解决方式

| 冲突类型 | 解决策略 |
|---------|---------|
| Git代码冲突 | 由后提交者负责merge，复杂冲突两人共同解决 |
| 技术方案分歧 | 列出方案优缺点，投票或请教老师 |
| 任务分配不均 | 每日回顾，动态调整 |
| 进度滞后 | 及时同步，必要时调整任务优先级 |

## 四、Git工作流规范

### 4.1 分支策略（Feature Branch Workflow）
main ← 主分支（仅通过PR合并，禁止直接提交）
└── develop ← 开发主分支（仅通过PR合并）
├── feature/user-module ← 用户模块（成员A）
├── feature/book-module ← 书籍模块（成员B）
├── feature/order-module ← 订单模块（成员A）
├── feature/comment-module ← 留言模块（成员B）
├── feature/frontend-login ← 前端登录页（成员A）
├── feature/frontend-books ← 前端书籍列表（成员B）
├── feature/frontend-orders ← 前端订单页（成员A）
└── feature/frontend-comments ← 前端留言页（成员B）

### 4.2 提交规范（Conventional Commits）

| 类型 | 说明 | 示例 |
|------|------|------|
| feat | 新功能 | `feat: 添加用户注册接口` |
| fix | bug修复 | `fix: 修复书籍分页bug` |
| docs | 文档更新 | `docs: 更新结对编程计划` |
| test | 测试相关 | `test: 添加用户模块单元测试` |
| refactor | 重构 | `refactor: 重构订单状态管理` |
| style | 代码格式 | `style: 格式化代码符合PEP8` |
| chore | 配置/构建 | `chore: 添加.gitignore` |

### 4.3 PR（Pull Request）规范

**所有功能分支必须通过 PR 合并到 develop，禁止直接 push 到 develop/main。**

- **PR标题：** 简洁描述本次功能
- **PR描述：** 包含"本次改动"、"测试情况"、"截图（如有）"
- **PR必须被另一人 review 后才能合并**
- **Reviewer 至少留 1 条评论**（可以是 LGTM、修改建议等）

## 五、结对编程模式

### 5.1 驾驶员-领航员（Driver-Navigator）模式

| 角色 | 职责 |
|------|------|
| **驾驶员（Driver）** | 实际敲键盘写代码，关注语法和当前逻辑 |
| **领航员（Navigator）** | 关注整体架构、风格、缺陷发现、下一步方向 |

### 5.2 角色互换规则

- **每 30-45 分钟必须互换一次角色**
- 互换时简短回顾刚才进度
- 每次 Pair 详细记录在 `3_角色互换日志.md`

### 5.3 单人开发场景

部分简单 CRUD 允许单人在自己的feature分支开发，但：
- 必须创建独立分支
- 必须通过 PR 由另一人 review
- PR描述中说明"单人开发原因"

## 六、风险与应对

| 风险 | 应对策略 |
|------|---------|
| 一方进度落后 | 另一方及时支援，结对完成 |
| Git合并冲突 | 频繁 pull develop，小步快跑提交 |
| 技术不熟悉 | AI辅助 + 查文档 + 互相教学 |
| 设备故障 | 代码及时push到远程，避免本地丢失 |
| 网络访问GitHub失败 | 使用国内镜像（kkgithub.com） |
